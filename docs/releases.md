## `v1.2.1` — CI 입력 잔존 수리 (2026-08-29 발행, patch·수리)

**한 줄**: GPU 검증 잡이 **이번 push 가 배송한 시나리오만** 검증한다. 그 전에는 **지난 실행에서
남은 시나리오 파일이 워크스페이스에 그대로 살아 있다가 같이 검증**됐다. **소비자는 아무것도
고치지 않는다** — `@v1` 이 이 태그로 옮겨졌을 뿐이고, 소비자 워크플로 문서 변경은 **0** 이다.

**증상** — 소비자가 시나리오를 **삭제한 push** 에서, 그 삭제된 시나리오가 **계속 검증됐다.**
p7c3 소비자 PR #4 2런째(run `33230008911`) 실측:

| 무엇 | 값 |
|---|---|
| 이번 push 가 배송한 시나리오 | **4** (`goal` · `goal_b` · `goal_random` · `obstacles_low_random` — 입력 아티팩트 실물) |
| 리포트가 담은 요청 | **5** |
| 5번째의 `request_identity_key` | `sha256:3e30cfbba88b…` = **1런째(`33177087506`)의 가구 시나리오 키와 동일** |
| 러너 워크스페이스 `scenarios/` | `Aug 29 11:52` 4개(이번 배송) + `Aug 28 22:52` **1개(어제 잔존)** |

**원인** — 두 사실의 곱이다. ① GPU 잡은 보안 경계(R10)상 **`actions/checkout` 을 하지 않는다**.
그런데 **그 checkout 이 워크스페이스를 비우던 유일한 단계**였다. ② `download-artifact` 는 기존
내용 **위에 병합**한다. 그래서 self-hosted 러너의 워크스페이스는 실행 사이에 살아남고,
`cv-infra submit scenarios/*.yaml` 의 글롭이 **잔존 + 신규**를 함께 집었다. **경고는 없었다.**
지금까지 드러나지 않은 이유는 단순하다 — 시나리오는 **추가만** 돼 왔고 이번이 **첫 제거**였다.
이 프로젝트가 **산출(artifact) 평면에서는 지켜 온 "잔존물 0"** 계약(p5c9)이 **입력 평면에는
없었다.**

**영향은 양방향이다** — 어느 쪽도 조용하다.
- 제거한 시나리오가 **계속 검증된다**(오늘 밟은 방향). PR 은 자기가 지운 문서 때문에 빨개질 수 있다.
- **깨져서 뺀 시나리오가 계속 통과를 만든다**. 검증 범위가 배송과 어긋난 채 초록이 유지된다.

**수리 (플랫폼 `verify.yml` 안, 2 스텝)**
- **워크스페이스 사전 청소** — 잡의 **첫 스텝**으로, 입력을 내려받기 **전에**
  `$GITHUB_WORKSPACE` 를 비운다(= checkout 이 하던 일의 명시적 복원). 지운 항목을 **전/후로
  로그에 찍고**(운영자가 "무엇이 사라졌는지" 읽을 수 있게), 비운 뒤 **0개임을 단정**해 실패하면
  거기서 멈춘다. 삭제 대상은 오직 `$GITHUB_WORKSPACE` 이며(입력에서 경로를 받지 않는다) 상대경로·
  `$HOME`·러너 work 루트 밖 등은 **거부**한다 — 프로덕션 데이터가 같은 호스트에 산다.
- **잔존 가드** — 제출 직전에 ⓐ 이번 실행의 청소 증적이 있는지, ⓑ 글롭이 **1개 이상** 집는지,
  ⓒ 집힌 파일이 **전부 이번 실행의 입력 아티팩트가 준 것**인지 확인하고, 어긋나면 **exit 2** 로
  멈춘다(배송 목록을 함께 출력해 육안 대조가 된다). 조용한 재발을 막는 게 이 스텝의 전부다.
- 이 수리는 **워크플로 YAML 평면에만** 있다 — 그래서 `@v1` 태그 이동만으로 소비자에게 도달한다
  (CLI/패키지에 넣었다면 러너 런타임 평면 재배포 전까지 닿지 않는다, G-43).

**소비자 조치: 없음**
- `uses: …@v1` 을 쓰는 소비자는 **다음 push 부터 자동으로** 수리된 워크플로를 받는다.
- **입력 계약 무변경**: `scenarios` 기본값 `scenarios/*.yaml`·`scenarios_artifact`·`sut_image`·
  `runner_label`·`api`·`timeout_s` 전부 그대로. exit 계약 **0/1/2/3** 그대로. 계약
  `apiVersion` = `cv-infra/v1` 그대로. CLI/패키지 축(`__version__`)도 `0.0.0` 그대로 —
  이번에 움직인 것은 **① Action 태그 축뿐**이다(R17, `docs/version-compatibility.md`).
- 다만 **접점 blob 은 바뀐다**(`v1.0.1` 이후 3 릴리즈 만의 첫 변경 — 아래 안정성 표 참조).
  바뀐 것은 잡의 **내부 스텝**이고 소비자가 적는 줄은 아니다.
- **행동이 달라지는 유일한 경우**: `scenarios` 로 **다운로드한 아티팩트 밖**(절대경로 등)을
  가리키고 있었다면 이제 **조용히 통과하지 않고 exit 2 로 멈춘다**. GPU 잡에는 애초에 아티팩트가
  준 파일만 존재하므로(R10, checkout 없음) 문서화된 사용법에는 해당이 없다.

**발견 경위** — p7c3 소비자 PR #4 **2런째**. 리포트의 요청 수(5)가 배송 수(4)와 맞지 않는 것을
PM 이 잡았고, `request_identity_key` 가 **전날 런의 키와 같다**는 점 + 러너 디렉토리 타임스탬프로
잔존이 확정됐다. 사람이 세어 보지 않았으면 드러나지 않았을 결함이다.

## `v1.2.0` — 장애물 종류·개수·yaw 랜덤 배치 (2026-08-28 발행, minor·가산)

**한 줄**: 시나리오가 **어떤 장애물을 몇 개 어느 방향으로** 놓을지 선언할 수 있게 된다
(*"의자 1 · 책상 n={0~5} · 지게차 2"*). `v1.1.0`의 랜덤성이 상자 1개의 x/y에 갇혀 있던 자리를
**종류·개수·yaw**로 연다. **기존 문서·워크플로는 수정 없이 그대로 동작한다.**

**가산된 계약 (전부 opt-in — 쓰지 않으면 오늘과 동치)**
- **`scenario.obstacles`** — 항목마다 `asset` + `count` + `x`/`y` + `yaw`.
  - **종류(`asset`)**: 큐레이션 레지스트리 이름 **`chair` · `desk` · `forklift`**(세 값 모두
    라이브 자산 루트에서 bbox·z_offset·콜라이더·동적물리를 **실측한 뒤** 등재됐다 — 기억으로
    경로를 적지 않는다) | 직접 `.usd/.usda/.usdz` 참조 | 내장 큐보이드 **`box`**. 해석 규칙은
    `scenario.scene`과 **동일**이고, 레지스트리 표는 **러너가 소유**한다(계약이 `Literal`로
    복제하면 자산 하나 추가가 곧 계약 변경이 된다).
  - **개수(`count`)**: 정수 또는 **`{randint: [lo, hi]}`** — **닫힌 구간(양끝 포함)**,
    `lo == hi` 합법 · `lo > hi` loud 거부. 상한은 `32`이며 **구조적 상한이지 측정값이 아니다**
    (`count` 오타 하나를 admit 단계 0 GPU초에서 죽이려는 값 — 올리는 것은 하위호환).
  - **`yaw`**: 이번에 열린 **새 랜덤 축**. `x`/`y`와 같은 어휘(`{uniform: […]}` /
    `{choice: […]}`)를 받고 기본값은 `0.0`.
  - `height/width/depth`는 **내장 box 전용**이다 — 비-box 자산에 선언하면 loud 거부한다
    (USD 자산은 자기 extent를 갖고 온다; 조용히 무시하지 않는다).
- **레거시 `debug_obstacle`와 택일**: 둘을 동시에 선언하면 **거부**하고, 에러가 목록으로
  옮겨 적을 dict를 그대로 렌더한다. 출하된 문서는 전부 단독 선언이라 영향 0.
- **파생 = 싱글턴 전개**: 그룹 하나가 `count`개의 `count: 1` 항목으로 평탄 전개된다(리스트
  위치 = 파생 순서 = 러너의 prim 배정 순서). **`n=0`은 합법** — 전개가 비면 키를 **소거**한다
  (빈 리스트는 쓰지 않는다).
- **장애물 접촉은 `no_collision`에 집계된다**(장애물 전용 지표를 만들지 않았다). 판정에서
  빼려면 그 오라클의 `params.collision_excluded_paths`에 **`/World/cv_obstacles`** 한 줄을
  추가하면 된다 — 풀 전체가 이 한 스코프 아래 산다. 실측: 근접 의자 → `collision_count=27`
  + 접촉 파트너에 `/World/cv_obstacles/chair_*/SM_Chair`, 코스 밖 → `0`·pass.
- **동적 물리 자산은 loud 거부**: `RigidBodyAPI`/`ArticulationRootAPI`를 실은 자산은 부팅
  시점에 거부한다. 무력화 사다리를 쓰지 않는 근거가 실측이다 — RigidBody 보유 prim에
  콜라이더를 얹으면 **접촉이 0**이 된다(유령 장애물). 등재 3종은 전부 RigidBody 0이라

  태그 메시지**에 박아 둔다(노트가 자기보다 나중에 측정된 값을 미리 적을 수는 없다).
  **게이트가 red 면 태그를 자르지 않는다** — *"clean host 에서 빌드되지 않는 릴리즈"* 는
  아래 `v1.0.0` 결함의 다른 얼굴이다(p6c5 선례: 죽은 apt 핀 1개로 태그를 멈췄고, 재핀 뒤에
  발행했다).

**이 릴리즈의 배포 주의 (v1.2.0 고유)**

- ⚠ **`@v1`을 옮기면 YAML 평면만 움직인다** — 런타임/러너이미지/제어평면 3평면은 재빌드·

## `v1.1.0` — 랜덤 시나리오 표기 + 배치 실행 (2026-08-27 발행, minor·가산)

**한 줄**: 시나리오가 **분포를 선언**할 수 있게 되고(`repeats`가 그 분포의 표본 수가 된다),
n표본이 **1잡 n반복**으로 실행돼 표본별 결과가 취합된다. **기존 문서·워크플로는 수정 없이 그대로
동작한다.**

**가산된 계약 (전부 opt-in — 쓰지 않으면 오늘과 동치)**
- **랜덤 표기**: 시나리오 8필드(`initial_pose.x/y/yaw` · `goal.x/y/yaw` · `debug_obstacle.x/y`)가
  스칼라 대신 `{uniform: [lo, hi]}` 또는 `{choice: [...]}` 를 받는다. **정적(스칼라) 문서는 dump
  바이트가 불변**이라 identity 키·회귀 baseline이 보존된다.
- **`repeats` 의미 정밀화**: `repeats: n` = **표본 n개**(선언 분포에서 파생). 정적 문서에서의 기존
  동작은 그대로다(같은 문서를 n번).
- **`min_pass_ratio`**(선택, 기본 없음): 표본 다수결 판정을 **Check 표면과 exit 계약 양쪽에 일관되게**
  도달시킨다. 미선언 시 오늘의 판정과 동치.
- **파생 스탬프**: 산출 문서에 `derivation: {version: "cv-derive/1", index}`. 표본별 독립 시딩
  `sha256("cv-derive/1:<seed>:<i>")` — 같은 seed면 같은 구체화 문서다. **제출본에 이 스탬프를 치면
  거부**한다(소비자가 친 스탬프는 신뢰하지 않는다).
- **배치 실행(내부 와이어)**: `JOB_SPEC_BATCH` 래퍼 문서 + `batch_summary.json`
  (schema `cv-batch-summary/1`) — 표본 n개를 컨테이너 1개에서 n반복으로 돈다. 기존 단일
  `JOB_SPEC` 경로는 **무변경**이다.

**무엇이 안 바뀌었나 (마이그레이션이 불필요한 이유)**
- 계약 `apiVersion` = **`cv-infra/v1`** 그대로(수용 테이블 무변경).
- exit 계약 **0/1/2/3** 그대로.
- 소비자 접점 2파일(`.github/workflows/verify.yml` · `actions/verify/action.yml`)이
  **`v1.0.1`과 바이트 동일**(측정: blob `e06a50fc…` / `7e684cf2…`) ⇒ `uses: …@v1` 핀만 쓰는
  소비자는 **워크플로를 한 줄도 고치지 않는다.**
- CLI/패키지 버전 축(`__version__`)은 **`0.0.0` 그대로**다 — 3축은 독립이고(R17), 이번에 움직인
  것은 **① Action 태그 축뿐**이다(`docs/version-compatibility.md`).

**릴리즈 게이트 (2026-08-27 실측)**
- 러너 이미지 **`--no-cache` 빌드 exit 0(96 s)** — 캐시 히트가 아니라 apt 핀 8/8이 실제로
  해석됐다(G-99 ①). 그 직전 빌드는 `curl=8.5.0-2ubuntu10.12` 철회로 **죽었고**, 이 릴리즈에는
  아카이브 직접 조회로 재핀한 `.13`이 들어 있다.
- 전체 스위트 **1440 passed** · 플랫폼 CI(소비자 의존 0) success.

⚠ **`@v1`을 옮기면 YAML 평면만 움직인다** — 런타임/러너이미지/제어평면 3평면은 재빌드·재설치로만
따라온다(G-43/G-88). 이 태그를 라이브에 태우기 전 `scripts/check_plane_skew.sh`로 대조하라.

## ⛔ `v1.0.0` — 결함 릴리즈 (2026-08-20 발행, 같은 날 대체됨)

**증상**: 이 태그로 **clean host에 재배포하면 소비자 검증이 `errored` 로 죽는다.**
제어평면 컨테이너에 러너 워크스페이스가 마운트되지 않아 `oracle_plugin_dir` 검증이 실패한다:

```
runner seam crashed: ValueError: oracle_plugin_dir <runner _work>/…/scenarios
  does not exist or is not a directory (expected the scenario directory holding
  the custom oracle .py, D-1)
```

**원인**: `docker/compose.yaml`에 소비자 입력 마운트가 **없었다.** p5c4가 이미 이 실패를 만나
`_work` 마운트로 고쳤으나 그 수리가 **손으로 친 `docker run -v`에만** 살아 있었고 compose에는
주석으로만 남았다. p5c14가 제품 경로로 교체하며 증발했다(6일 잠복, GOTCHAS **G-94**).

**수리**: `b6aa979` — compose 마운트 5→6(소비자 러너 `_work`만 `:ro`). ⇒ **`v1.0.1`**.

**왜 `v1.0.0`을 지우거나 옮기지 않았나**: 그 태그는 *불변* 으로 선언돼 발행됐다. 발행된 불변 태그를
사후에 다른 바이트로 바꾸면 **핀의 의미 자체가 죽는다**(누가 `v1.0.0`을 받았는지 알 수 없다).
대신 **여기에 결함을 명시**하고 수정 릴리즈를 낸다 — 이것이 표준 관행이다.

⚠ `v1.0.0`의 **태그 메시지 자체에 죽은 단정**이 들어 있다(*"운영 평면 … 이 커밋으로 구동 중"* —
발행 18분 뒤 거짓이 됐다). 불변 객체는 고칠 수 없으므로 **이 문서가 그 정정본**이다.
**교훈**: 릴리즈 태그는 *"지금 운영에서 도는 것"* 을 단정하지 마라 — 운영은 움직이고 태그는 안 움직인다.
